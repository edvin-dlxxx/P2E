## A1. Source of truth and Figma governance

*Replaces v1.3 §2.1 for appearance questions.*

| Question | Decides |
|---|---|
| Appearance: colors, typography, icons, sizes, spacing, radii, variants, states | **Figma** |
| Structure: layers, state, routing, testing | **Architecture v1.3 + Addendum v1.4** |
| Anything decided later | `decisions.md` (newer entry wins) |

Rules:

1. **Figma is read-only** for the development team and its agents. Nobody writes to the design file from tooling.
2. **Figma inconsistencies are not copied into code.** A typo, a missing Light/Dark twin or a one-off value is logged in
   `errata.md` with a "code handling" rule. The designer resolves it (R-007). Known items at this date: E-001 … E-010.
3. **Names.** Dart names follow Figma names, with typos corrected (`Countainer/Teal` → `containerTeal`, `Samll Badge` →
   `smallBadge`). The raw Figma name stays in the generated mapping, so the Inspector can show it.
4. **Behavior gaps.** Figma does not define loading, error, empty and offline states, keyboard behavior, focus order or motion
   timing. For each gap the team proposes an option, the owner approves it, and it is logged in `decisions.md`.
   Nobody invents a design silently.
5. **Versions.** The designer publishes a named Figma version for each delivery. Each version gets a committed snapshot
   (`design/figma/<snapshot>/`) and a diff report (A4).
6. **Master file.** The team currently reads a copy of the design file. Read access to the master file is requested (R-005).
   When it is granted, the file key in `docs/agents/figma-map.md` changes, and a new snapshot is taken.

Note: v1.3 §15.5 names Inter as the wireframe font. Figma uses **Outfit**, so Outfit is the Latin font (A3.4).

## A2. Scope confirmations

*Resolves OD-7. Updates v1.3 §2.3, §2.4, §15.4 and §16.3.*

### A2.1 Theme

- **Dark and Light both ship in the MVP.** "To be confirmed" in v1.3 §2.4 is removed.
- The default theme mode follows the OS. In settings the user can choose **System / Light / Dark**. The choice is stored
  in `shared/preferences` (v1.3 §15.4, unchanged).
- **Design gap:** the 12 Authentication / Login frames, and the `Base Password Field` and `OTP Field` sets, exist only in
  Dark (E-008). Their Light versions are requested from the designer (R-001, high).
  - Until the designs arrive, the Light versions are derived from the Light tokens and shown as `provisional` in the Inspector.
  - **Fallback:** if R-001 is not delivered by launch, the MVP default theme mode becomes **Dark**. The user can still choose Light.

### A2.2 Tablet and orientation

- Tablet support is **architected**: size classes, `AdaptiveScaffold`, `AdaptiveGrid` and maximum content width (v1.3 §16).
- **No tablet layouts are invented.** Until the designer delivers Medium/Expanded layouts (R-006), only the safe rules apply:
  maximum content width, and more grid columns in game lists. Anything beyond that would be thrown away when the real design arrives.
- **Orientation:** phones are portrait-only. Tablets (Medium/Expanded) allow portrait and landscape. The v1.3 §16.3 requirements
  for resizing and multi-window on tablets remain.
- D-003 is `provisional`: it may change when the tablet design arrives.

## A3. Localization, RTL and typography

*Resolves OD-8. Updates v1.3 §11.3 and §15.5.*

### A3.1 Release order

- **English is built first. Persian ships later.**
- Until Persian ships: `supportedLocales = [en]`, and every device locale falls back to `en`. Only `l10n/app_en.arb` exists.
  `app_fa.arb` is added when the Persian work starts.

### A3.2 Persian-ready from day one

Building RTL only "on paper" would force a rework of padding and layout in every component later. The following is
therefore required **now**, while it is cheap:

- **Directional APIs only:** `EdgeInsetsDirectional`, `AlignmentDirectional`, `BorderRadiusDirectional`,
  `PositionedDirectional`, `TextAlign.start/end`. A physical left/right needs `// PHYSICAL: reason`. **CI enforces this** (A11.2).
- Every component appears in the Gallery and in golden tests in **RTL with Persian sample text**, next to LTR/English.
- Typography tokens are keyed by script/locale, so Persian can get its own font and scale without changing components.
- **Icon mirroring:** directional icons (arrows, chevrons, back/forward) mirror automatically in RTL. The mirroring flag is
  stored in the icon registry, not at call sites.

### A3.3 Default locale and first-launch language picker ✅ owner-approved

Many users in the target market keep the phone in English but want the app content in Persian.
The OS locale alone is therefore not a reliable signal.

**Decision:**

1. On the first launch, the app starts with the **OS locale**, if it is supported. Otherwise it starts with `en`.
2. A **first-launch language picker** lets the user confirm or change the language before onboarding.
3. **Settings (N06)** gets a language row, so the user can change the language at any time.
4. The language switches at runtime. `Directionality` follows the locale (v1.3 §15.5). No app restart is needed.

**Startup gate.** The picker is a new gate in the startup state machine (v1.3 §11.3), **before** onboarding:

```
initializing
  → versionCheck ──(unsupported)──────────────────→ updateRequired (X07)
  → localeSelection ─(not chosen, >1 locale)──────→ languagePicker (new, R-002)
  → firstLaunchOnboarding ─(not seen)─────────────→ onboarding (E01–E04)
  → … (unchanged from v1.3)
```

| Gate | Read model | Updated by |
|---|---|---|
| localeSelection | `localeChosen` flag + chosen locale (`shared/preferences`) | `entry` (picker), `profile` (settings row) |

Rules for the gate:

- **It is active only when `supportedLocales` has more than one entry.** In the English-only MVP it is skipped, and no picker
  screen ships. It switches on with the Persian release, without a code change in the controller.
- The choice is a **device preference**, not an account preference. Logout and account switching (`SessionTeardown`,
  v1.3 §10.4) must not clear it.
- The gate works offline: it reads only a local flag.
- **Design dependency:** the picker screen and the settings row are requested from the designer (R-002, medium).
  The design must arrive before the Persian release.

### A3.4 Fonts

*Replaces the font paragraph in v1.3 §15.5.*

- **Latin: Outfit**, as used in Figma. It replaces Inter.
- **Persian: Vazirmatn** is bundled now as a **provisional fallback**. Without it, Persian user content during the English phase
  (for example a nickname) would render in each OS's own font, and iOS and Android would look different.
- The final Persian font and type scale come with the Persian design (R-003). D-006 is `provisional` until then.
- Fonts stay bundled. No runtime font download (v1.3 §15.5, unchanged). Licenses are checked before release.

## A4. Design tokens pipeline

*Adds to v1.3 §15.4. The `SkinDefinition` model and the test skin remain.*

```
Figma (named version) → design/figma/<snapshot>/ (JSON) → tool/tokens/ generator → lib/ui/tokens/generated/
```

- **Tokens are generated, never typed by hand.** To change a token, fix the snapshot source (new Figma version) or the generator,
  then regenerate.
- The snapshot is committed, pretty-printed with stable ordering, and never edited after commit. Every new snapshot gets a
  diff report against the previous one.
- **Light/Dark color tokens** come from the two parallel semantic collections in Figma. In Figma, Light and Dark are separate
  component sets, not variable modes. In code, brightness is one theme axis (v1.3 §15.4).
- Naming follows A1.3. Group names are corrected too (`----- Supportin Colors -----` → `supporting`, E-007).
- Product tokens that Material lacks stay in `ThemeExtension`s (v1.3 §15.4, unchanged).
- Motion tokens (durations, curves) are `provisional` until the designer delivers motion specs (R-008).

## A5. Component rules

*Updates v1.3 §15.2.*

1. **Parameters mirror Figma variant axes as Dart enums.** Free `Color`, `TextStyle`, `EdgeInsets` or size `double` parameters
   for visual choices are not allowed.
2. **Only combinations that exist in Figma are valid.** An invalid combination fails an `assert` in debug builds.
3. **Button color is a parameter:** an enum of the colors in Figma. The default is the original Figma color.
4. **Light/Dark is never a component parameter.** Components read brightness from the theme. The Figma axis `Theme` (and its
   misspelled twin `Therme`, E-003) is ignored in code.
5. Every public Design System widget carries an **`ElementIdentity`**: component id, variant values, Figma node id, and status
   `final` | `provisional`. It also has an entry in the generated spec registry (A8).
6. **Components without a Figma design** (currently Switch, Checkbox, Tabs, Chip, Card, Sheet, Dialog, Toast) are built from
   tokens on top of themed Material widgets, marked `provisional`, and sent to the designer's queue now (R-004).
   This prevents provisional components from becoming permanent by default.
7. **Text scaling** is supported up to **1.3×** and clamped above. *Replaces "up to 200%" in v1.3 §15.2.*
   - The clamp is applied once at the app root (`MediaQuery` text scaler).
   - **Trade-off, accepted by the owner:** this is below the 200% accessibility target in v1.3. The design layout is preserved,
     but users who need very large text get less help.
8. The "component catalog (optional Widgetbook)" in v1.3 §15.2 is replaced by the **Component Gallery** (A8).

All other v1.3 §15.2 rules stay: all interactive states, 48 dp touch targets, semantics, RTL safety, no business logic, no Riverpod.

## A7. Icons

*Updates v1.3 §15.6. Replaces the earlier `material_symbols_icons` recommendation.*

- Icons are **SVGs exported from Figma**: Outline and Fill, **104 × 2**, with identical names in both styles (E-010).
- They are stored in the repo under `assets/icons/system/` and always load locally.
- They are used **only** through `AppIcon(AppIconId.x, style: …)`. `Icons.*`, `CupertinoIcons.*` and icon packages are not allowed.
- A build step may compile the SVGs to an icon font or to `vector_graphics`. This renders faster and takes color and size from the theme.
- The main benefit is an exact match with the design and support for custom icons. (A package would also have been bundled locally.)
- The icon registry holds the RTL mirroring flag for each icon (A3.2).

## A8. Dev Inspector and Component Gallery (new v1.3 §15.7)

Both tools exist from the component stage onward. They are **dev-only**.

### A8.1 Isolation

- They live in `lib/dev/` and are imported **only** by `lib/main_dev.dart`.
- `lib/main.dart` (release) must never reach `lib/dev/`, so tree shaking removes the tools from release builds.
  `tool/check_architecture.dart` enforces this import rule.

### A8.2 Inspector

- **Off by default.** A small overlay control turns it on. When off, it must not change layout or timing.
- For a tapped widget it shows: component id, variant values, Figma node id (as a link), status (`final` / `provisional`),
  the **expected** values from the spec (size, padding, radius, colors as token + raw Figma name, text style, icon) next to the
  **measured** values, and a per-property result: match / mismatch / not measurable.
- Expected values come from `lib/dev/specs/generated/`, built from the Figma snapshot. Nobody types expected values by hand.
- It compares at text scale **1.0** and with the theme of the inspected subtree.

### A8.3 Component Gallery

- A dev-only screen in `lib/main_dev.dart`, next to the Inspector.
- It lists every component and every **valid** variant combination ×
  **Light/Dark** × **LTR (en) / RTL (Persian sample text)** × **Compact / Medium**, plus the test skin.
- Golden tests render from the same Gallery entries (A11.1).

### A8.4 Limits

- The Inspector is a manual tool. It only helps when someone looks. **Golden tests in CI** are the automatic safety net.
- The dev entrypoint is slower. Performance is checked regularly in **profile/release** builds, because dev builds hide speed problems.

## A9. Platform adaptation

*Replaces v1.3 §17.1 and updates the table in v1.3 §17.2.*

### A9.1 Principle

**Same look, motion and interaction on iOS and Android.** This replaces "same brand look, platform-native behavior".
There is no separate Cupertino UI (unchanged).

### A9.2 Updated behavior table

| Behavior | Android | iOS / iPadOS | Change vs v1.3 |
|---|---|---|---|
| Back | System / predictive back via `PopScope` | Edge-swipe back | Unchanged, now a registered exception (PE-002). |
| Page transitions | **One shared transition** | ← same | Changed: was per platform. |
| Scrolling | Stretch overscroll | Bounce | Unchanged, now a registered exception (PE-001). |
| Haptics | Same pattern | Same pattern | Unchanged. |
| Hover / focus | Optional | Optional | Unchanged. |

### A9.3 Approved platform exceptions ✅ owner-approved

| Id | Area | iOS | Android | Reason |
|---|---|---|---|---|
| PE-001 | Scroll physics / overscroll | Bounce | Stretch | Users feel it physically. It changes no visual design. |
| PE-002 | System back | Edge-swipe back | System / predictive back via `PopScope` | Each OS requires it. |

Rules:

- Page transitions (`PageTransitionsTheme` with the same builder for every platform) and scroll behavior (one `ScrollBehavior`
  implementing PE-001) are set **once** in `MaterialApp`.
- Platform-specific code exists only in `lib/app/platform`, marked `// PLATFORM(PE-###): reason`, with an entry in
  `platform-exceptions.md`. `Platform.isX`, `dart:io` and `defaultTargetPlatform` branching are not allowed in `lib/ui`,
  `lib/shared` or `lib/features`.
- Per-platform behavior built into Flutter widgets (text selection handles, context menu, keyboard) is accepted.
  If one changes look or motion in a way the owner would notice, the team proposes a new PE entry instead of patching it.
- A new exception is added only after testing shows a real problem.

### A9.4 Scope of the "same on both platforms" promise

The promise covers **appearance and interaction**. It does not cover every business flow. App Store rules on payments and
rewards may force a different purchase or reward flow on iOS (OD-4, unchanged). Such a difference is a capability or
flag decision (v1.3 §17.2, §19.5), not a platform exception.

## A10. Override policy (new v1.3 §15.8)

- **Choosing another existing token is free.** It is not an override.
- A **raw visual value** (color, size, padding, radius, duration) outside `lib/ui/tokens/` is an override. It needs:
  - an annotation `// OVERRIDE(O-###): reason`, and
  - an entry in `overrides.md` with a "remove when" condition.
- This applies to responsive layout too.
- CI lists every override, and fails for annotations without an entry and entries without code.

## A12. Implementation roadmap: Phase 2

*Updates "2. Design System v0" in v1.3 §21. Other phases are unchanged.*

Building the whole Design System before the first real screen would reveal parameter design problems too late.
Phase 2 therefore runs in this order:

1. **Tokens.** Generated by script, complete. Light and Dark, plus the test skin.
2. **`AppButton`, `AppTextField`, `AppBadge`.** With Gallery entries, goldens and Inspector specs.
3. **Pilot screen "Login with Email - Dark".** It uses almost only these three components. It is the first real test of the
   component parameters and of the Inspector. Lessons go back into the component contract and the build skills.
4. **Remaining components:** App Bar, Navigator, Games components, and the provisional components (A5.6).
5. **English screens** (Phases 3–8, as in v1.3).
6. **Persian and tablet** layouts, when their designs arrive (R-003, R-006).

**Phase 2 exit criteria (updated):** the pilot screen passes a clean Inspector check in Light and Dark. Goldens are green for
the full matrix. Dark and tablet scope are confirmed (done, A2). The ID crosswalk and missing wireframes are tracked (OD-12, unchanged).

No step starts early without the owner's approval.
